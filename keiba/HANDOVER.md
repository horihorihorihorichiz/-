## 0. これは何のシステムか

ユーザー（堀川さん）と共同開発している競馬予想・運用システム。**目的はただ一つ「競馬で勝つ（プラス収支）」**（FORMAT_FINAL.md §0でユーザーと合意済み）。
2週間・13,194レースの実測により「確定オッズの情報だけでは控除率20-25%を超えられない」ことを確定させ、現在は**発火表方式**（期待値プラスの証明がある時だけ買い目を送る・普段は見送り）で運用中。

## 4. 堀川システムの計算方法（Ver.99.27）

**正典**: 計算コード= `calc.py`（501行）、手作業手順= keiba-yosou スキル（STEP0〜STEP10）、
馬柱→入力jsonの変換規則= `SOP.md`。以下はその要約。

### 4-1. 16成分（1頭ごとに算出）

| 成分 | 意味（1行） | 定義箇所 |
|---|---|---|
| TSI | タイム指数（今回条件に近い過去走の最良値・距離係数補正） | calc.py:181 |
| LTS | 近走着順スコア（最良着順＋中央競馬繰上＋ブースト） | calc.py:167 |
| FSI | 脚質×枠の適合（芝=内枠有利／ダ=砂被りロジックで差・追は外枠クリーン評価） | calc.py:199 |
| Bonus | 実績加点（該当実績 0/8/10点） | calc.py:214 |
| DSI | 距離適性（近3走±200m掲示板=A → 1年以内 → ±400mの3段） | calc.py:225 |
| NSI | 格（クラス実績グレード） | calc.py:151 |
| CSI | コーナー通過統計 | calc.py:189 |
| WAS | 斤量（出走馬プール内比較・最軽量判定） | calc.py:242 |
| TAS | 道悪適性（1年以内の稍/重/不着順でA〜C） | calc.py:259 |
| HCS | 斤量・条件調整 | calc.py:278 |
| NRJA | ローテ（休養日数） | calc.py:289 |
| 展開乗数 | ペース5段階（スロー〜ハイ）×脚質の相性 | calc.py:41,328 |
| spd_res / mgn_abs / wide4c / pos_gain | コーナー系4成分（スピード残し/着差絶対値/4角外回し/位置取り上昇） | v99w2_fit.py |

脚質確定=STEP1（finalize_styles）、展開=STEP2（pace_stage）が先に走る。

### 4-2. 得点＝配点との内積（hori52・2層方式）

1. 16成分をレース内でZ正規化 → ベクトル **Z16**
2. 重み **w = 0.5 × w52[場+芝ダ+距離帯] + 0.5 × w30[芝ダ+距離帯+クラス]**
   （該当セルが無ければ w6[芝ダ×距離帯] → 全体1本 へフォールバック）
3. **得点 = Z16 · w**。同点タイブレークは (−得点, −WAvg, 馬番)
4. 重みの実体= `hori52_w.json`（49セル2層）、人間可読の実効配点表= **`HORIKAWA_FULL.md`（1,088行・1枚で完結）**
5. **配点を書き出し・変更したら必ず `python3 verify_export.py`**（規律R1。selfcheckが監視、
   サボると❌になる。過去に書き出しでクラス層が潰れ成績が1pt落ちる事故があった）

### 4-3. 得点から予想への変換

- **PWin**: 得点をソフトマックス的に確率化（predict.py/day_board.py内）
- **ランク**: S/A/B/C/D（PWin分布から）。チャットに出す時は**全頭・全列**（絶対5項目の1）
- **形**: レース内SDで正規化した上位段差 g12=(1位-2位)/SD, g23, g34
  → 1強(g12≥0.6)/2強(g12<0.3∧g23≥0.6)/3強/混戦/階段
  → **当てにいく型は形で選ぶ**: 1強→複勝1位／2強→ワイド1-2／3強→三連複123／混戦→見送り

## 5. 買い判定（2系統ある・混同するな）

### 5-1. 憲章の「買い目」＝PLUSエンジン（plus_fires.json）
期待値プラスの**証明**がある発火だけ「買い目」としてLINE送信。書式
`場R / 券種 / 買い目 / 金額 【S or A】根拠`（S=2万/A=1万）。**現在active=G4の1本のみ**:
- **G4 = WIN5キャリーオーバー**: 繰越が想定売上の約43%超（≈8.6億円）の日曜だけ、
  `win5.py --budget 10000` のフォーメーションを【A】で送る。JRAで唯一証明可能な+EV。
- G2（直前資金シグナル）/G3（91.8%セル×ドリフト補正）は9月中旬・3,000Rで判定待ち。
- **発火なしの日は買い目を送らない＝正常動作**。期待値負の提案は必ず`[参考・期待値負]`ラベル。

### 5-2. 検証中レーン＝凍結パターン（patterns.py・紙上前向き測定中）
乖離単勝系（モデル1位が単勝7倍+等）のパターン集。`classify()`→`heat_of()`→`tier_of()`で
SS(2万)/S(1万)/A(5千)/B(千円)を出す。**発火条件は2026-08-16に凍結・変更は全破棄**
（PATTERNS_FROZEN.jsonのsha256で監視）。
⚠**前向き成績は50件で回収52.5%**（採掘時主張205%）。金額増額禁止・9月に降格判定。
⚠**買い/取消の正はpaper_rank.pyのT-25凍結記帳のみ**。day_boardの再分類は表示専用
（8/23にこの二重ソースで「取消」と誤案内→唯一の的中を逃す事故。MEMORY.md参照）。

## 6. 開催日の運用手順（毎週土日）

正典= FORMAT_FINAL.md §3 と ROUTINE.md冒頭の「週末フルオート」プロンプト（Routinesに登録して使う）。要点:
1. **6:30 JST 最優先**: `nohup bash keep_alive.sh oddsMMDD 200 python3 -u odds_timeline.py watch >> logs/... &`
   （番人経由必須。プロキシポートが日に数回変わり裸のnohupは死ぬ）。「NNレース/予定NNN時点」を目視。
2. selfcheck → line_notify --check → day_board.py
3. 発火あれば即通知、**T-25〜15で再判定(confirmed化)**。紙上並走: paper_rank/watch_log/v99w_rank/w12_watch の run
4. 全レース後: 各settle&stats → odds_timeline settle/stats/compact → デイダイジェスト1通 →
   まとめmd送付 → MEMORY.md追記 → commit&push
5. ユーザーの役割は**LINEの【S/A】を買うだけ**。購入・投票・GOは常に人間。

## 7. 検証規律（これを破った数字は全部ゴミになる・実証済み）

- **R1** 書き出した配点はverify_exportの機械検証まで使わない
- **R2** null（偽データ対照）は実データと同じ自由度で作る
- **R3** 掃引したら「最良を選ぶ手続きごと」nullで再現。勝者は新データ1回測定まで未確定
- **R4** 上乗せは必ずSE併記。1SE未満を「明確」と書かない
- **凍結の哲学**: 事前情報だけで作った高ROIでも、本物と偶然は見た目で区別できない
  （実力ゼロの偽データから同じ採掘でROI200%が量産できることを実測）。
  区別する唯一の方法が「先に買い目を凍結→後から結果」。205%→52.5%がその実例。
- **恒久禁止**: 単勝120倍超／三連複BOX手広／18頭乖離系／モデル確率×オッズの期待値
  （実回収と相関−0.925）／穴軸の組合せ券種／開催初日／期待値負を「買い目」として送る。

## 10. 落とし穴集（全部実際に踏んだ）

1. **コンテナリセット**が日に数回起きる。長時間プロセスは keep_alive.sh 経由・成果は即push・
   *.pklとline_token.localは消える前提。復旧はリモート正のff-merge（「Updating...」の後に
   Abortingが出ていないか必ず確認。8/23朝はこれを見落として半日古いコードで走った）。
2. **LINEトークン**はリセットで消える→ユーザーに再依頼。恒久対策=環境設定のEnvironment
   variablesに`LINE_CHANNEL_TOKEN`を登録してもらう（line_notify.pyは環境変数を最優先で読む）。
3. **netkeiba無料オッズは41-55分遅延**。直前判定はJRA公式(sp.jra.jp)系の取得を使う。
4. 出力に**nullバイト**が混ざることがある→ `| tr -d '\0'`。
5. `bash -c "A && B & C"` は `(A && B) & C` に解釈される（cdが背景側に入る）→ ログパスは絶対パスで。
6. 同じ台帳を触るrunの**並走禁止**（後勝ちで消える）。逐次の二重実行は冪等で安全。
7. 買い/取消の**二重ソース禁止**（§5-2の事故）。
