作成 **2026-08-18（火・JRA非開催日に実地検証）**／対象: `odds_timeline.py`・`jra_odds.py`
事前登録された分析計画は **`ODDS_DRIFT_PROTOCOL.md`**。この文書は「どう作ったか・どう回すか」。

## 0. 結論（3行）

1. **主系列は JRA公式（sp.jra.jp）。netkeibaは併走サンプルとしてだけ使う。**
   netkeiba無料オッズは実測40-50分遅れ（2026-08-16計測）なので、**最も知りたい直前1時間が丸ごと見えない**。
   ただし netkeiba は `official_datetime`（＝そのオッズの実時刻）を返すので、**時刻ラベル付きの
   遅れた観測**として捨てずに使う（分析は wall clock ではなく odds_time を軸にする）。
2. **SNAP_MINUTES を確定**: light（単勝・複勝・ワイド）= `180/90/60/45/30/20/15/10/7/5/3/2`、
   heavy（三連複）= `60/30/15/7/3`、netkeiba併走 = `25/6`。**1日36レースで684時点**。
   実測コストでの負荷シミュレーションで **稼働率21%・取り逃し0.1%**（§2）。
3. **終点は「取る」のではなく「後で無料でもらう」**。パリミュチュエルなので払戻は確定オッズで決まる。
   確定オッズは netkeiba が過去レースに対して無制限に返す（`COMBO_ODDS_NOTES` §1）。
   よって `settle` で FINAL＋着順＋払戻を後追い追記する設計にし、**締切ギリギリのポーリングを減らした**。

## 1. どちらのソースを使うか（決着）

| | netkeiba 無料API | JRA公式 sp.jra.jp |
|---|---|---|
| 更新 | **実測40-50分遅れ**（2026-08-16・単勝） | 1-2分毎 |
| リクエスト数 | **全券種7本**（三連複560点も1本） | 単複1・ワイド1・**三連複は(頭数-2)本** |
| 所要 | 6-9秒 | light 2-5秒 / heavy 28-36秒 |
| 過去レース | **無制限に遡れる**（確定オッズ） | **当日+直近開催のみ** |
| 実時刻の分かる印 | `official_datetime` あり | `asof`（"18:01現在"/"最終"/"確定"） |

### 決定
- **T-180〜T-2 の主系列 = JRA公式。** 理由は単純で、netkeibaでは
  「発走40分前〜締切」という**この研究の核心部分のオッズが物理的に存在しない**から。
  40-50分遅れのデータで T-3 のオッズを名乗ることは、数字の捏造と同じ。
- **netkeibaは T-25 / T-6 に併走サンプルとして残す。** 目的は3つ:
  (a) **遅延を毎レース実測する**（`odds_time` と取得時刻の差。`stats` が中央値を出す）。
      `COMBO_ODDS_NOTES §4(A)` が「8/22に必ず実測」と宿題にしていた項目を、手作業ゼロで満たす。
  (b) **組合せ券種の遅延が単勝と同じか**を確かめる（未検証だった）。
  (c) JRA公式が落ちた・構造変更された日の**保険**（遅れてはいるが時刻付きの観測は残る）。
- **FINAL は netkeiba。** 8/18の検証で、JRA公式の「最終」表示と netkeiba 確定オッズは
  **8/16の2レース・全1,195点（単16/複16/ワイド120/三連複560 ×2R）で完全一致**（比1.000）。
  終点の定義に食い違いは無い。

## 2. SNAP_MINUTES の最終決定と根拠

```python
SNAP_LIGHT = [180, 90, 60, 45, 30, 20, 15, 10, 7, 5, 3, 2]   # 単勝・複勝・ワイド（2req・約4秒）
SNAP_HEAVY = [60, 30, 15, 7, 3]                              # 三連複（頭数-2 req・約30秒）
SNAP_NK    = [25, 6]                                          # netkeiba併走（7req・約7秒）
```

### なぜこの配置か

1. **後半を密に、前半を疎に（対数的配置）。** 資金流入は締切直前に集中する。
   間隔は 90→45→30→15→10→5→3→2→1 と、発走に近いほど短くした。
   「等間隔（60/45/30/20/15/10/5/3）」は前半に無駄が多く後半が粗い。
2. **T-15 と T-3 を必ず含める。** それぞれ `paper_rank.py` の**直前判定**（0<tminus≤25 で confirmed）と
   **凍結**（発走3分前 `odds_at_freeze`）の時刻。同じ時刻の値を持っておくと、
   紙上運用の記帳と**そのまま突き合わせられる**（別々の時刻で測ると比較にならない）。
3. **T-1 / T-0 は取らない。** 三連複1回に約30秒かかるので T-1 に置くと締切をまたぎ、
   「締切前の値」なのか「締切後の最終値」なのか判別できない行が生まれる。
   最終値は `settle` が netkeiba から**無料で・確実に**取れるので、直前を削っても情報は落ちない。
4. **T-180 / T-90 を入れた理由。** 「早い時点のオッズが系統的に短い/長いだけ」という
   最も退屈な説明（ODDS_DRIFT_PROTOCOL §3 M2）を潰すには、プールが未成熟な時間帯が要る。
   light は2リクエストなので、ここを厚くしても負荷にならない。
5. **三連複を light の部分集合に絞った理由。** 1時点30秒 × 全12時点 = 6分/レース は
   3場開催では回らない。ドリフト曲線の形を見るのに必要な最小限（早期・T-30・直前判定・凍結）に絞った。
   間引く時は `--max-axis 4` で軸ページを減らせる（実測: 14頭で 31秒→8秒・カバー率67%）。
   その場合 `trio_full=false` が記録され、**一次分析からは自動的に外れる**。
6. **前日・当日朝のアンカーは今回入れていない。**
   JRA公式のオッズインデックスは「当日＋直近開催」しか載せない（実測: 8/18時点で 8/15-16 の6開催を掲載中）。
   **前日オッズが載るかどうかは金曜にならないと確かめられない。**
   → 8/21（金）夜に `python3 odds_timeline.py probe` を回して、8/22の開催が掲載されているか確認する。
     載っていれば T-720 相当のアンカーを1点足す（`SNAP_LIGHT` の先頭に追加するだけ）。
     **確認できるまで「前日オッズが取れる」とは書かない。**

### 負荷（実測コストでのシミュレーション）

8/16（土）の**実在する36レースの発走時刻**でスケジュールを組み、実測所要時間で回した結果:

| profile | heavy所要の想定 | 予定時点 | 取り逃し | 稼働率 |
|---------|----------------|---------|---------|--------|
| full | 34秒（実測値） | 684 | **1件 (0.1%)** | **21%** |
| full | 45秒（遅い日の想定） | 684 | 13件 (1.9%) | 29% |
| lite | 34秒 | 540 | 0 | 20% |
| lite | 45秒 | 540 | 0 | 28% |

**取り逃しは T-90 と T-180 にしか出ない**（遅い想定でも T-60/45/30/20/15/10/7/5/3/2 は 0件）。
スケジューラを「**締切に近い予定を先に、同時刻なら安い方を先に**」で並べたため、
混雑時に犠牲になるのは必ず遠い時点になる。遅れの中央値は light 0.00分 / heavy 0.15分、90%点でも1.3分。

リクエスト数の見積り（1日・3場36レース）:
`sp.jra.jp` ≒ **3,170**（light 864 + heavy 約2,160 + 開催ページ更新 144）、
`netkeiba` ≒ **504**。8時間に均すと sp.jra.jp へ **約0.11 req/s**。
`jra_odds.SLEEP = 1.0秒` はそのまま（＝人がオッズ画面を見る程度の頻度）。

## 3. 実地検証で見つけて直した欠陥

| # | 欠陥（改修前の `odds_timeline.py`） | 影響 | 対処 |
|---|---|---|---|
| 1 | **netkeiba（`predict.fetch_jra`）だけを叩いていた** | 40-50分遅れ＝**直前1時間のオッズが1点も取れない**。研究そのものが不可能 | 主系列をJRA公式に。netkeibaは時刻ラベル付き併走サンプルへ降格 |
| 2 | `odds_time` は記録していたが**券種別 `odds_time_by_type` を捨てていた** | 券種ごとに遅延が違った場合に検出できない | 併走サンプルに両方を保存 |
| 3 | **再開できない**（`done` がプロセス内メモリだけ） | 落ちて上げ直すと**同じ時点を二重記録**し、遠い時点を取り直して直前を取り逃す | `attempts_of()` が当日ログから (rid,tag,kind) を復元。取得済みはスキップ、2回失敗した点は諦める |
| 4 | **二重起動できてしまう** | 心拍とルーチンが両方 watch を起こすと外部サイトを2倍叩く | `odds_timeline/.watch_<date>.lock`（PID・生存確認つき）。`--force` で上書き可 |
| 5 | **取消・除外を検出しない** | 出走取消でプールが組み替わった変化を「ドリフト」として集計してしまう | 各時点の `runners` を保存し、前時点との差を `scratched` に記録。`drift()` は既定で該当遷移を除外 |
| 6 | **取れなかったことが記録に残らない**（`tan` が空なら `return None`） | 「発売前」「取止め」「こちらの障害」の区別がつかず、欠測が沈黙する | `ok=false` + `reason` の行を残す。同一レースで連続3回失敗したら以後の予定を破棄（無駄打ちを止める） |
| 7 | **1分ループ＋「m-2≤tmin≤m」判定** | 1回30秒の三連複が入るとループが伸び、**T-3 が T-0 にずれる**。ずれても記録は "T-3" のまま | 予定表を先に作り、締切の近い順に消化。許容遅れ（light 2分 / heavy 3分）を超えた点は**捨てる**。実測の `t_minus` と `t_minus_end` を毎行に記録 |
| 8 | **発走時刻を起動時に1回しか読まない** | 発走遅延が起きた日に全時点がずれる | `LIST_TTL=600秒`ごとにレース一覧を取り直して予定を作り直す |
| 9 | **単一ファイル追記・fsyncなし** | 落ちると末尾行が壊れる／年で数百MBの1ファイルになる | 日別 `odds_timeline/YYYYMMDD.jsonl`、`flush+fsync`、`compact` で古い日をgzip（読み出しは透過） |
| 10 | **ナビゲーションを毎回やり直す** | 1回のlightに6秒の無駄。3場36レースでは回らない | `jra_odds.fetch_day_page()` を新設し、開催ページHTML（全レース×全券種のcnameを含む）を20分キャッシュ。三連複の軸cnameもレース単位でキャッシュ。**light 11.7秒→4.3秒、trio 34.3秒→27.7秒**（実測） |
| 11 | `stats` が壊れていた（ループ外の `tags` 参照、`FINAL` タグで `int(t[2:])` が例外、最初と最後のタグしか比較しない） | 集計できない | 事前登録された時点対（§ODDS_DRIFT_PROTOCOL §4）を券種×オッズ帯で集計するよう書き直し。Σ(1/オッズ) の時点推移も追加 |
| 12 | **light と heavy が同じキーで衝突**（改修中に実地テストで発見） | 単複ワイドを取ると**同じ時点の三連複が「取得済み」扱いになり永久に取れない** | 予定キーに `kind` を含める（`ev_key`）。集計側も同一tagのlight/heavy行を**上書きではなく合流**（`index_rows`）。selftest に回帰テストを追加 |
| 13 | 集計がソースを混ぜていた | 遅れているnetkeibaの値がJRA公式の同じタグに合流し、時刻の意味が壊れる | `index_rows(src="jra")` を既定に。`src=None` 時はタグを `T-30@netkeiba` のように分離 |

### 検証したこと（すべて実データ）
```
python3 odds_timeline.py selftest   # オフライン: 予定生成/再開判定/取消除外/light-heavy衝突/ドリフト算術
python3 odds_timeline.py probe      # 実地: JRA公式に掲載中の直近開催レースで light/heavy/nk を実行
```
- `probe`（202607020811・中京11R・16頭）: light **8.1秒/4.8KB**（単16・複16・ワイド120+上限120）、
  heavy **36.2秒/10.2KB**（三連複560点）、nk **6.0秒/16.1KB**。全て `ok=True`。
- `watch` ループの実地テスト（発走時刻を「3分後」に見せかけて実在レースを収集）:
  T-2 の light/heavy/nk が3行とも記録され、2回目の起動で**再取得ゼロ**（再開判定OK）。
- `settle` の実地テスト（8/16の2レース）: 確定オッズ・3着内・払戻（三連複 24,150円 / 219,000円）を追記。
- `stats`: Σ(1/オッズ) が **単勝1.265（理論1.250）・三連複1.337（理論1.333）** と払戻率に一致。
  集計コードが正しく暗黙確率を再構成できていることの確認になる。

### ディスク見積り（実測サイズから）
1レース **約156KB** → **1日5.5MB / 1週末11MB / 1年(52週) 572MB**。
gzip 実測比 **1/5.4** → `compact` 後で **年106MB**。
```bash
python3 odds_timeline.py compact --keep-days 14   # 2週間より古い日をgzip（読み出しは透過）
```
`hist_odds/`（8,465ファイル）と同程度の規模で、リポジトリに置ける範囲。
これ以上絞りたいときは `--profile lite`（684→540時点）か `--max-axis` を使う。

## 4. 既存の運用と競合しないか

| 相手 | 叩く先 | 同時実行の可否 |
|------|--------|---------------|
| `paper_rank.py run` | netkeiba（一覧・馬柱・オッズ）＋凍結時のみ sp.jra.jp（3req） | **競合しない。** odds_timeline の netkeiba へのアクセスは1日504リクエスト（T-25/T-6のみ）。sp.jra.jp 側は 0.11 req/s で余裕がある |
| `watch_log.py run` | netkeiba（day_boardのキャッシュ共有） | 同上 |
| `day_board.py` | netkeiba | 同上 |
| `notify.py --heartbeat` | ローカルのみ | 無関係 |

- `odds_timeline.py` は **予想ロジック・買い目・通知に一切触れない**。書き込むのは `odds_timeline/` だけ。
- `jra_odds.py` への変更は **引数追加のみ**（`day_html=` / `axis_cnames=` / `fetch_day_page()`）。
  既存呼び出し（`predict.fetch_jra(fresh=True)`・`selfcheck` の到達確認・`paper_rank` の凍結）は
  引数を渡さないので**従来と完全に同じ経路**を通る。戻り値に `axis_cnames` / `trio_axes` が増えたが
  既存キーの値は変えていない。
- `predict.py` には**触っていない**。

## 5. 土曜の起動手順（8/22 から）

```bash
cd keiba
python3 selfcheck.py                     # ALL GREEN を確認してから始める
python3 odds_timeline.py watch --dry     # ★まず予定を目視（レース数と時点数。36R/684時点が目安）
nohup python3 odds_timeline.py watch > logs/odds_timeline_$(date +%Y%m%d).log 2>&1 &
```
- **朝いちばん（1R発走の3時間前 = 6:30-7:00 JST）に起動する。** T-180 から取り始めるため。
  遅れて起動しても問題はない（過ぎた時点は「取り逃し」として捨て、残りから収集を始める）。
- **落ちても、そのまま同じコマンドで上げ直してよい。** 取得済みの時点はスキップされる（`attempts_of`）。
  二重起動はロックで自動的に止まる。
- **全レース終了後**:
  ```bash
  python3 odds_timeline.py settle          # 確定オッズ+着順+払戻を追記（1レース約1秒）
  python3 odds_timeline.py stats           # まず Σ(1/オッズ) の推移を見る（PROTOCOL §3 M2）
  ```

### 心拍 / Routine から回す形
`watch` は**長時間常駐するプロセス**なので、8分間隔の心拍から毎回起動する形には向かない。
心拍からは「**生きていなければ起こす**」だけにする（冪等・二重起動はロックが防ぐ）:

```bash
# 心拍のたびに1行。既に動いていればロックで即終了する（外部サイトを余分に叩かない）
cd keiba && pgrep -f "odds_timeline.py watch" >/dev/null || \
  nohup python3 odds_timeline.py watch >> logs/odds_timeline_$(date +%Y%m%d).log 2>&1 &
```
- `--until HH:MM` を付ければ、その時刻で自然終了する（例: `--until 17:30`）。
- 収集の成否は**ログではなくデータで**確認する（`stats` の「時点別」件数が各タグ 30件前後あれば健全）。
- **`notify.plan()` は使わない。** これは買いレースの通知台帳であって、収集ジョブの生死は
  そこに混ぜない（RULES §通知 1. の「レースID×種別の正規通知のみ」を汚さないため）。

## 6. まだ確かめていないこと（8/22に必ず見る）

1. **発売中のページでパーサが動くか。** 8/18の検証はすべて `asof="最終"`（締切後）のページ。
   発売中は「---」や別クラスが混ざる可能性がある。→ 朝いちの T-180 で `ok=false` が続いたら
   `python3 jra_odds.py <race_id> --combo --debug` でHTMLを確認する。
2. **前日オッズの有無**（§2-6）。8/21（金）夜に `probe` で判定。
3. **取消・除外のあるレースで三連複が全点そろうか。** 実装は `<select>` の**並び順**の末尾2つを
   落とす方式で欠番耐性を入れてあるが、実レースでの確認はまだ。→ `trio_full` と
   `sanrenpuku` の点数が C(頭数,3) と合うかを `stats` の「点」列で確認する。
4. **netkeibaの遅延が組合せ券種でも同じか。** `stats` の最後に出る
   「netkeiba無料オッズの遅延」で自動的に実測される（`kind="nk"` の行のみ対象）。
