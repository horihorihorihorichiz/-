# 前日予想 → 当日オッズ照合 → 連絡

## 全体の流れ

```
前日夜  ローカル（有料ページが読める）
        出馬表と調教評価を取り、hori_w.json で採点
        → keiba/predictions/YYYYMMDD.json を push
              ↓
当日朝  クラウド（このリポジトリを読む側）
        無料APIで単勝オッズを取り、並びと突き合わせる
        → 食い違ったレースだけを連絡
```

有料ページはローカルからしか読めず、当日のオッズは無料APIで誰でも取れる。
その境目でちょうど作業が分かれる。

## 前日にやること（ローカル）

Claude Code にこれを貼る。

### JSONの形

```json
{
  "date": "20260829",
  "source": "weights/hori_w.json (24成分・採用段階 L1)",
  "note": "同一レース内の並びのみ。買い目ではない。plus_fires.json 未作成。",
  "races": [
    {
      "race_id": "202604030311",
      "name": "新潟11R",
      "post": "17:30",
      "shape": "1強",
      "horses": [
        {"rank": 1, "num": 15, "name": "レッドレガリア", "score": 2.9, "eval": "好調持続"}
      ]
    }
  ]
}
```

`rank` は同一レース内の並び順、`score` は得点、`eval` は追い切りの短評。
`race_id` は netkeiba のもので、これでオッズを引く。

## 当日にやること（クラウド側で自動）

```
python keiba/tools/oddscheck.py 20260829
```

単勝オッズを取り、次の2つに当てはまるレースだけを挙げる。

| 印 | 条件 | 意味 |
|---|---|---|
| ○ | 並び3位以内 かつ 6番人気以下 | システムは推すが市場は評価していない |
| ▲ | 1番人気 かつ 並び5位以下 | 市場は推すがシステムは評価していない |

線は `oddscheck.py` の冒頭 `TOP_N` / `COLD_RANK` / `DOUBT_RANK` で変えられる。

食い違いが0件なら「見送りが妥当」と出る。**それが正常な日も多い。**

## これは買い目ではない

`plus_fires.json`（発火表）が未作成である限り、買う根拠は存在しない。
このツールが挙げるのは「システムと市場の意見が割れたレース」であって、
そこに賭ければ儲かるという意味ではない。

実測（`system/logic.md`）:

```
3着内率   24成分 59.64%  vs  市場 66.14%
上乗せ    最大 0.0019 nats  （控除率20%を越えるには 0.223 nats 必要）
```

2026-08-29 の新潟11Rでは、`g12=1.10` の「1強」判定にもかかわらず
並び1位のレッドレガリア（1.6倍）が掲示板を外し、84.6倍が勝った。
形の判定は信頼度の保証ではない。

## 次にやるべきこと

食い違いを見つけるだけでは足りない。**その食い違いが過去に儲かったかを
台帳10,551レースで検証する**のが発火表づくりで、それができて初めて
「買い」と言える。

検証の型:

1. 条件を1つ決める（例: 調教評価「好調持続」かつ 6番人気以下）
2. 学習期間ではなく**未知期間 1,740R** で単勝・複勝の回収率を出す
3. 控除率を越えているか、越えているならサンプル数は足りるか
4. 越えた条件だけを `plus_fires.json` に載せる
