## ★★ 2026-07-26 V4作り替えの確定事項（詳細=MODEL_V4_RESULT.md）★★
1. **JRAの tier は {3,4,5,6,10} しか無い**。tier3=OP/重賞 4=3勝 5=2勝 **6=1勝** 10=未勝利新馬。
   patterns.py の `6 <= tier <= 9` は「上級」ではなく**1勝クラスちょうど**。数字は正しくラベルが誤り。
2. **「オッズを使わずに市場を上回る」は現時点で不可能**（願望ではなく測定結果）。
   選択バイアスを外した全2200R比較: 三連複1-2-3位 モデルV4 76.5% < 市場1-2-3人気 77.8%。
   モデル1位の勝率は市場implied比 **-2.2pt**（V3は-3.0pt）。
   → パリミュチュエルで控除率を超える道は「市場より正確に推定する(a)」か
   「市場の価格ズレを突く(b)」の2つだけ。(a)は測って負けたので、**残るは(b)＝オッズ必須**。
3. **部分集合のROIで「勝てる」と言わない**。必ず①全レース比較で選択バイアスを外し、
   ②`rule_audit.py --null-sweep` で「実力ゼロの偽データ」から同じ採掘をやり直して偽陽性率を測る。
   実例: オッズ不使用の三連複ルールが164.8%に見えたが、偽データでも平均14.8件・最高ROI中央値236%が
   出るため**棄却**した。この検定をやらなければ実弾に載せていた。
4. **馬場は必須入力**。同一ルールで 良148.1% / 道悪51.4%。道悪は「今日の水分量への適性」という
   未観測変数が支配し、過去走ベースの序列が崩れる。**開催初日も買わない**（誰も馬場を読めない）。
   **馬場問題の解決一式(7/27 baba_impact.py実測・全てコード化済み)**:
   - 確認: `python3 day_board.py --baba` = 今日の全開催場の現在馬場を1コマンド表示(発走前チェックの度に叩く)
   - **単勝系の金脈(10倍+×1勝/実用コア/メイン4場/中距離)は道悪でも生存**(道悪n計7-12で各250-816%)→ゲート不要

   - 芝馬連1600-1800は稍で警告表示(dev214→conf49不安定/27R)。芝三連複は従来通り良限定
   - 過去走の馬場は baba_idx(良0稍1重2不3) として保存する(fetch_race/harvest修正・従来は全走None=損失)。
     既存hist 6,701件の過去走babaは復元不可(既知)。今後の収穫分から蓄積される
5. **V4(model_v4_s0..4.txt)は既定にしない**。`KEIBA_ENGINE=v4` で明示有効化。
   理由: patterns.py の g12閾値はV3の生スコア基準。V4は得点の意味が変わる（二値＝勝ち馬確率のz）
   ため、**g12系パターンの再採掘が済むまでV3のまま**。オッズ系パターンは再確認済みで維持〜改善。

   順位バグ（外枠2位27.2% > 1位24.4%）を拾っていたもの。V4では逆転が消えた（1位25.4% > 22.0%）。

## §通知・運用の恒久ルール（2026-08-15 事故4件からの教訓・全セッション/ルーチン厳守）
1. **通知台帳(notify.py)**: 買いレースが決まったら即 notify.plan() で「15分前通知/凍結/当落」を予定登録。
   通知を出した直後に notify.mark()。心拍は毎回 notify.check() を呼び、欠落があれば即送信。
   「別の報告に1行混ぜた」は送信実績にならない——レースID×種別の正規通知のみがmark対象。
2. **心拍は8分間隔・会話/通知のたびにCronListで生存確認**、消えていたら即再作成
   （ワーカー再起動は起床予約と心拍を同時に消す。8/15に2回発生）。
3. **チャット=正**: 通知内容は必ずチャットに全文。プッシュは到達保証がない「気づかせる係」。
   S/A級はプッシュ2連発（15分前+10分前）。
4. **障害レース除外**: 「障害」表記だけでなく JUMP_RE=障害|ジャンプ|JS で判定（新潟JSすり抜け事故）。
5. **環境リセット復旧**: paper_rank.py欠損を検知したら ff-merge+pip install -q numpy lightgbm。
   復旧前に判定・通知をしない（古いコードでの判定事故防止）。
6. **オッズ配信停止の扱い(2026-08-16)**: predict.fetch_jraの戻りに ng_reason が入る(例 "empty free odds schedule"=netkeiba側で場単位の無料オッズ配信停止)。オッズ0件のときは必ずng_reasonを確認し、通知には「取得失敗」ではなく**配信停止(外部要因)か自システムの障害かを区別して明記**する。配信停止中のレースは判定不能=見送り(オッズ無しで買わない)。復旧は心拍で自動再試行。
7. **停止ギャップ検出は心拍の義務(2026-08-17制定・8/16の28分停止で中京12Rの通知が飛んだ事故)**:
   心拍・セッション復帰のたびに `python3 notify.py --heartbeat`（またはコード内 `notify.sweep()`）を呼ぶ。
   - 最終実行時刻を notify_state.json に刻み、**20分以上の空白＝実行基盤停止**として検出。
     停止中に期限を迎えた予定は `gap.missed` に列挙されるので、復帰した瞬間に必ず点検・送信する。
   - `notify.check()` は**日付をまたいだ18時間分の遅延**まで返す(late_min/stage付き)。
     「期限がとっくに過ぎているから」と黙って落とすことを禁止する。送る意味が無くなった予定は
     `notify.close(rid, kind, reason=…)` で**明示的に取り下げて記録に残す**(黙殺しない)。
   - `notify.plan()` には post(発走時刻)も渡す。遅延検出時に「未発走=まだ送れる/発走後=手遅れ」を
     機械が区別できるようにするため。
   - selfcheck.py は未送信の期限超過通知が残っていると ❌ を出す。週末はALL GREENで入る。
8. **W10/W11のライブwatchは賭け金ゼロで全レース記録(2026-08-17新設・watch_log.py)**:
   `python3 watch_log.py run` を当日の記帳サイクル(発走15-25分前)で paper_rank.py と一緒に回す。
   **一致レースだけでなく不一致(対照群)も記録**する——対照群を取るまで「発見」と呼ばない(8/17に
   W10の最高tsi版が対照群で消滅した実例)。台帳は watch_log.jsonl（paper_rank_log.jsonl と完全に別）。
   数字は必ず[ライブ実測]と[窓内=参考値]を分けてラベルする。買いルールには入れない([候補]止まり)。
