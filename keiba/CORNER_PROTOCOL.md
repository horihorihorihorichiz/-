## 0. 背景と仮説

2026-08-18 に `fetch_race.py` を拡張し、過去走レコードから次の4項目を新たに保存できるようにした。

| 項目 | 内容 | 従来 |
|---|---|---|
| `corner_all` | 通過順の全区間 `[11,11,10,7]` | 4角の `7` だけ保存し他を捨てていた |
| `pace_first` / `pace_last` | そのレースのペース前後半3F `30.3 / 36.9` | **完全に未取得** |
| `run_time` | 走破タイム（秒） | 未取得 |
| `margin` | 着差（秒） | 未取得 |

既存の `hist/*.json` は旧パーサ製なのでこれらを持たない。よって**再収穫**が要る。

仮説: 「道中どう動いたか」「どんな流れを経験したか」「どれだけの差で負けたか」は
市場（オッズ）が完全には織り込んでいない可能性がある。PASTRUN 検証（27特徴）は
**着順と4角位置しか見ていない**ため、この4項目は原理的に未検証である。

## 1. 再収穫の設計（実装前に確定）

1. `fetch_race.fetch_shutuba(rid, nar=False)` で各レースの `horse_id` を取得（レースあたり1リクエスト）。
   → `corner_ids.json`（`{rid: {umaban: horse_id}}`、原子書き込み・中断再開可）
2. ユニークな `horse_id` について `fetch_race.fetch_horse_results` を**1回だけ**呼び、
   全キャリアを `horse_cache/{horse_id}.json` に保存。基準日 `2030-01-01` 固定で取得し、
   各レコードに実施日 `_pdate` を付与する（レース日に依存しないキャッシュにするため）。
3. 各レースについて、キャッシュから「そのレース日より前（`days>0`）の9走」を切り出し、
   `hist/<rid>.json` の `horses[].races[]` に **`days` で照合して新4項目だけを追記**する。
   既存の値（finish/field/corner4/agari/tier/pace/baba_idx/tsi/vg）は**上書きしない**。
   併せて `horses[].horse_id` を保存する。書き込みは一時ファイル→`os.replace` の原子書き込み。
4. レート制限に配慮（同時4スレッド・各リクエスト後 0.4 秒スリープ）。進捗は 100 件ごとにログ。
5. 対象は `wf_preds_v3ext2.jsonl` の **5,990レース**（2024-2026）を優先。時間が許せば `hist/` 全体へ拡張。

**再収穫が時間内に終わらない場合は、取れた分だけで検証し「n=◯レース分での結果」と明記する。**

## 2. 検定する特徴（全10本・実装前に確定／以後追加禁止）

すべて as-of（過去走レコードのみ。当該レースの結果は一切使わない）。
記号: 過去走 `r` について `ca = r["corner_all"]`、`F = r["field"]`、`ff = r["finish"]/F`（0=勝ち, 1=最下位）。
`mean(ca)` は通過順の平均。**直近5走**を既定の窓とし、必要な項目が欠けている走は除外する。
値が作れない馬は `None` → レース内z標準化で 0（＝平均扱い、`fit_v2.z_in_race` と同規約）。

| # | 名前 | 定義 | 必要本数 |
|---|---|---|---|
| 1 | `pos_gain` | 直近5走の `(ca[0] − ca[-1]) / F` の平均。**正=道中で位置を上げる馬** | `len(ca)≥2` の走が1本以上 |
| 2 | `pos_var` | 直近5走の `std(ca) / F` の平均。**大=道中で動く馬** | 同上 |
| 3 | `wide4c` | 直近5走の `(ca[-1] − ca[-2]) / F` の平均。**正=最後の角で位置を下げる（外を回す）** | 同上 |
| 4 | `pace_lv` | 直近5走の `pace_first` の平均（秒）。**小=速い流れを経験** | 1本以上 |
| 5 | `pace_gap` | 直近5走の `pace_first − pace_last` の平均。**負=前傾（前半速い）ラップ経験** | 1本以上 |
| 6 | `fwd_fin` | `pace_first < pace_last`（前傾ラップ）だった過去走（最大9走）の `−ff` 平均。**大=速い流れで粘れる** | 1本以上 |
| 7 | `mgn_abs` | 直近5走の `abs(margin)` の平均（秒）。**小=僅差の競馬をしている** | 1本以上 |
| 8 | `spd_res` | 直近5走の「速度残差」の平均。速度 `= dist / run_time` (m/s)。as-of ベンチ表 `(馬場, dist//200, baba_idx)` の平均速度との差を ±2.5 でクリップ。標本30未満は `(馬場, dist//200)` → `(馬場)` にフォールバック。**正=そのクラス・条件で速い** | 1本以上 |
| 9 | `grind` | 直近5走のうち `mean(ca)/F ≤ 0.4` **かつ** `abs(margin) ≤ 0.5` の走の**割合**。**大=先行して粘る** | 判定可能な走が1本以上 |
| 10 | `unlucky` | 直近5走の `ff − mean(ca)/F` の平均。**正=位置が良いのに着順が悪い（不利を受けた推定）** | `len(ca)≥1` の走が1本以上 |

**合計 10本。これ以外を後から足さない。**

as-of ベンチ表（#8）は `pastrun_feats.AgariBench` と同じ規約で構築する
（日付が進んだ時にだけ反映＝同日レースも参照しない、前日以前のみ）。

## 3. 検定手順（PASTRUN_PROTOCOL.md と同一・1本ずつ単独投入）

### 3-1. データ
- 台帳 `hist/*.json` のうち **新4項目の再収穫が済んだレース**のみ。
  「済んだ」の定義 = そのレースの全出走馬について `horse_id` が判明し、
  かつ少なくとも1頭の1走以上に `corner_all` が入っていること。
- `result.order` に着順・確定オッズがある / 5頭以上 / 1着が特定できる レースのみ。
- 市場確率 `pm = (1/odds)` をレース内で合計1に正規化（控除率補正）。オッズ欠損馬がいるレースは除外。

### 3-2. 分割（月次・以後変更禁止）
| 分割 | 期間 |
|---|---|
| MINE | 〜202602 |
| VALIDATE | 202603〜202605 |
| CONFIRM | 202606〜202608 |

各分割の実レース数・馬数は結果表に必ず出す。**n<30 は参考表記**とし判定に使わない。

### 3-3. モデル（市場を条件にしたロジスティック回帰）
目的変数は2つ: `y_win`（1着=1）と `y_top3`（3着内=1）。**馬単位**の行。
- ベースライン共変量: `[1, log pm]`（`y_top3` は `[1, log pm, log(3/field)]`）
- 検定モデル: ベースライン + **候補特徴のレース内z**
- Newton-Raphson で最尤推定し、増分対数尤度 `ΔLL` と候補特徴の z値（`coef/SE`）を記録。

### 3-4. 判定（事前登録・変更禁止）
| 段 | 基準 |
|---|---|
| MINE 通過 | `\|z\| ≥ 2.5` |
| VALIDATE 通過 | MINE通過分のみ・**VAL期間だけで再推定**し **MINEと同符号** かつ `\|z\| ≥ 2.0` |
| CONFIRM 通過 | VAL通過分のみ・**CONF期間だけで再推定**し **MINEと同符号** かつ `\|z\| ≥ 2.0` |
| 特徴の合格 | 3段すべて通過 |

VALIDATE / CONFIRM は各**1回だけ**実行する（再実行・条件変更は禁止）。

### 3-5. 多重比較
- 総試行数 = 10特徴 × 2目的 = **20**
- MINE の偶然期待 = 20 × P(|z|≥2.5) = 20 × 0.012419 = **0.248**
- VAL の偶然期待 = (MINE通過数) × P(同符号 かつ |z|≥2.0) = (MINE通過数) × 0.022750
- **バッチ判定**: VAL通過数 ≥ 3 × VAL偶然期待 かつ VAL通過数 > 0 なら「偶然では説明できない」と見なす。
  下回れば、個別に合格した特徴があっても**採掘の副産物**として扱う。

## 4. V10（合格特徴を V3 に足したモデル）

**作る条件（事前登録）**: 「MINE と VALIDATE の**両方**を通過した特徴が **1本以上**」のときだけ作る。
1本も無ければ V10 は作らず、その旨を報告に書く（ゼロならゼロと書く）。

### 4-1. 構成
- 一段目 V10 = 条件付きロジット（レース内 softmax・1着尤度）
  入力 = `fit_v2.build_row(..., v4=False)` の V3 行（28特徴 + field） **＋ 通過した本プロトコル特徴（レース内z）**
- 比較対照 V3 = **同じ推定器・同じフォールド**で V3 行のみ
- 学習は月次ウォークフォワード（各評価月について、その月より**前**のレースのみで学習）

### 4-2. α の測り方（V7 二段構成と同じ）
評価月ごとに二段目 `u_i = α·log p_model_i + β·log p_market_i` を条件付きロジットで推定する。
**α>0 = モデルが市場に情報を足している**。

- フォールド = 評価6か月 `202603, 202604, 202605, 202606, 202607, 202608`
- **一次合格 = α>0 が 3フォールド連続**（V7・PASTRUN と同じ基準）
- `α(V10)` と `α(V3)` を並べ、**差**を必ず報告する。
  α(V10) > 0 でも α(V3) と同水準なら「新特徴の寄与はゼロ」と書く。

## 6. 事前に分かっている限界（先に書いておく）

1. 短距離戦は `corner_all` が2区間しかない（3-4角のみ）。`pos_gain`/`pos_var`/`wide4c` の情報量は
   距離によって不均一で、`wide4c` は2区間戦では `pos_gain` の符号反転と同一になる。
2. `pace_first/pace_last` は**そのレース全体の**前後半3Fであり、その馬個体のラップではない。
   よって「その馬が速い流れを経験した」ことは分かるが「その馬自身が飛ばした」かは分からない。
3. `margin` は netkeiba の着差列（勝ち馬は次位との差で負値）。単位系の混在は `abs` で吸収する。
4. `run_time` は同一レースの他馬と共通の絶対時計であり、馬場差・展開差を含む。
   as-of ベンチ表で条件補正するが、当日の馬場差までは補正しきれない。
5. 再収穫はレート制限のため数時間を要する。終わらない場合は取れた分だけで検証し n を明記する。
