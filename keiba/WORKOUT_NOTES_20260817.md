## 2. タイム列の仕様（★検算結果）

### 2.1 骨格：「累計 / 次カラムまでのラップ」の交互並び

スラッシュ区切りの値は **累計タイムとラップが交互** に並ぶ。
ラップは常に「その累計 − 次の累計」（最後だけ「1F − 0」＝ラスト1Fそのもの）。

**検算結果: 194行・770ラップすべてで残差 0.0（丸め誤差すらゼロの完全一致）。**

```
$ python3 workout.py verify premium_workout_20260816.txt
  "rows": 194, "laps": 770,
  "max_residual": 0.0,
  "worst_residual_row": null
```

### 2.2 依頼文の仮説「29.0 = 3F通過41.6に対する直前2Fラップ」→ **正しい**

```
72.0/15.9/56.1/14.5/41.6/29.0/12.6/12.6
 5F=72.0  →  4F=56.1   72.0-56.1 = 15.9 ✔
 4F=56.1  →  3F=41.6   56.1-41.6 = 14.5 ✔
 3F=41.6  →  1F=12.6   41.6-12.6 = 29.0 ✔  ← ここだけ 2ハロン分
 1F=12.6  →  0         12.6      = 12.6 ✔
```

これは例外ではなく**構造的な仕様**。netkeibaの周回コース調教テーブルに **2Fカラムが無い**
（列は 6F/5F/4F/3F/1F）ため、3Fの直後のラップだけが2ハロン区間になる。周回コース全行で一貫。

判別指標として「**最後から2番目のラップ ÷ ラスト1F**」を測ると:

| コース | n | 中央値 | 範囲 | 解釈 |
|---|---:|---:|---|---|
| 函W | 50 | 2.10 | 1.88–2.31 | 2F区間 |
| 札ダ | 45 | 2.15 | 1.87–2.50 | 2F区間 |
| CW | 26 | 2.27 | 2.02–2.48 | 2F区間 |
| **栗坂** | **65** | **1.02** | **0.91–1.15** | **1F区間（別レイアウト）** |

### 2.3 ★重要な訂正：坂路は列構成が違う（依頼文の「要素数だけで判定」は不十分）

依頼文の指示は「要素数から開始ハロンを判定（10=6F/8=5F/6=4F/4=3F）」だったが、
**これは周回コース系にしか当てはまらない。** 坂路（栗坂・美坂）は 800m＝4ハロンしかなく、
列が `[4F, 3F, 2F, 1F]` で、**全ラップが1ハロン分**。

```
栗坂: 56.9/17.1/39.8/14.4/25.4/13.0/12.4/12.4   （8要素）

× 要素数だけで判定（5F開始とみなす）
    5F=56.9 / 4F=39.8 / 3F=25.4 / 1F=12.4
    → 秒/ハロン = 11.38 / 9.95 / 8.47 / 12.40
      **3F を 25.4秒（8.47秒/F）** ＝ 物理的にあり得ない

○ 坂路レイアウト [4F,3F,2F,1F]
    4F=56.9 / 3F=39.8 / 2F=25.4 / 1F=12.4
    ラップ 17.1 / 14.4 / 13.0 / 12.4（全部1F）
    → 秒/ハロン = 14.22 / 13.27 / 12.70 / 12.40 ＝ 栗東坂路として完全に正常
```

**残差チェックだけでは、この誤りは検出できない**（交互構造は誤レイアウトでも成立するため
残差は0.0のまま）。そこで v0.2 では独立した2本のガードを入れた:

1. **秒/ハロンレンジ**: 全カラムで `10.0 ≤ cum/F ≤ 23.0` を要求。誤読の 8.47 はここで落ちる。
2. **tail_ratio**: 3Fの直後が2F区間になる並びなら比 ≥1.6、そうでないなら <1.6 を要求。

レイアウトは第一にコース名（`坂` を含む／`COURSE_TABLE`）で決め、上記2本で自動検算する。
現スナップショットでは `layout_suspect_rows: []`、秒/ハロン範囲は **10.90–15.15** で全行正常。

## 3. 実装した特徴（`workout.FEATURE_COLUMNS`）

### 3.1 生の量（コース差を吸収していない）
`f6 f5 f4 f3 f2 f1`（累計秒）, `last_1f`, `last_3f`, `last_4f`,
`mid_2f`(=f3−f1), `mid_2f_per_f`, `f3_per_f`, `f4_per_f`, `start_f`

坂路と周回でカラム構成が違うため、派生量は **列を直接読まず `f3 − f1` のような差で作る**。
これで両レイアウトから同じ意味の量が取れる（坂路には2Fカラムがあるが、周回と揃えるため使わない）。

### 3.2 標準化終い（コース差の吸収 = 本命の設計）

`z_last_1f`, `z_last_3f`, `z_mid_2f_per_f`

同一 **(コース, 馬場)** 内の平均・標準偏差で z を取り、**符号を反転**（高い＝速い）。
母数が4頭未満なら `コース → 種別(wood/dirt/slope) → 全体` に段階フォールバックし、
どの粒度が使われたかを `z_last_1f_group` / `z_last_1f_n` に必ず残す（後から監査できるように）。

実測のフォールバック状況: `course_baba` 183 / `kind` 6 / `course` 3 / `all` 2。
主力コース（函W・栗坂・札ダ・CW）は最も細かい粒度で足りている。

### 3.3 レース内相対順位（標本が小さいうちの主力）

`pr_last_1f`, `pr_last_3f`, `pr_accel`, `pr_z_last_1f`
（0〜1のパーセンタイル、1.0＝そのレースで最良。`_rank` と `_of` も併記）

- **利点**: 分布の仮定が要らず、n=194でも安定する。
- **欠点**: 同一レース内でも各馬の追切コースはバラバラ（函W vs 札ダ vs 栗坂）なので、
  `pr_last_1f` はコース差を吸収しない。**`pr_z_last_1f`（z を取ってからレース内順位）を推奨**。

### 3.4 余力指標（脚色の織り込み）

**係数は事前に固定**（データを見て決めていない）:

| 脚色 | 乗算係数 `EFFORT_COEF` | 加算ボーナス `EFFORT_BONUS` |
|---|---:|---:|
| 馬也 | 1.00 | +0.30 |
| G強 | 0.90 | +0.10 |
| 直強 | 0.90 | +0.10 |
| 仕掛 | 0.85 | 0.00 |
| 強め | 0.85 | 0.00 |
| 一杯 | 0.70 | −0.30 |

思想は依頼どおり「**馬なりで速い＝余力あり**を高得点に、一杯に追ってようやく出した時計は
額面どおり評価しない」。

- `reserve_mult_1f` / `reserve_mult_3f` = z × 係数 ← **依頼仕様どおりの乗算版**
- `reserve_add_1f` / `reserve_add_3f` = z + ボーナス ← **推奨する加算版**

> **⚠ 乗算版の既知の病理（報告書に明記せよと指示のあった点）**
> z は平均0の両側スケールなので、z<0 の馬に 0.70 を掛けると **値が0に近づく＝評価が上がる**。
> つまり「一杯に追って遅かった馬」が「馬なりで遅かった馬」より高く出てしまい、符号が反転する。
> 加算版にはこの問題がない。両方を出力してあるので比較できるが、**既定は加算版を使うこと**。

### 3.5 終い加速度

- `accel_1f_vs_3f` = (f3/3) ÷ f1 … 3F平均ラップ ÷ ラスト1F。>1 なら終いに向けて加速。
- `accel_1f_vs_2f` = ((f3−f1)/2) ÷ f1

> **⚠ 冗長性**: `accel_1f_vs_2f = (3·accel_1f_vs_3f − 1)/2` で、**実測相関 1.000000**。
> 同様に `f3_per_f` は `last_3f` の定数倍。**f3 と f1 から取れる独立な「加速度」は1つだけ。**
> モデルに両方入れてはいけない。`accel_1f_vs_3f` だけ使う。

### 4.1 帰無検定（RULES.md の作法どおり、偽陽性率を先に測る）

複勝ラベルを**レース内でシャッフル**して同じ採掘を400回やり直し、15特徴の `max|z|` の分布を出した:

```
観測 max|z| = 1.36
帰無分布   : 中央値 1.66 / 90%点 2.48 / 95%点 2.70
family-wise p = 0.745
```

**観測された最大の z（1.36）は、実力ゼロの偽データの中央値（1.66）にすら届いていない。**
つまり現時点で「調教特徴が効いている」ように見える兆候は**一つも無い**。
ただしこれは「効かない証拠」でもない — §6のとおり検出力がゼロに近いので、
効いていても見えないのが当然である。

### 4.2 記述クロス集計（検定なし・セルが小さすぎる）

```
-- 複勝率 by 脚色
   馬也 n=119 rate=0.202 / 強め n=27 rate=0.148 / 一杯 n=26 rate=0.231
   仕掛 n=13  rate=0.154 / G強  n=8  rate=0.375 / 直強 n=1  rate=1.000
```

- 「馬也 > 一杯」という**事前に期待した向きは出ていない**（0.202 vs 0.231）。係数の妥当性は未検証。

### 4.3 市場との重なり

`R2_mkt`（各特徴が単勝オッズで説明される割合）は全特徴で **0.001〜0.054**。
調教タイムは市場価格とほとんど相関していない。

これは二通りに読める。①市場が調教を織り込んでおらず**独立情報として使える余地がある**、
②単に調教タイムに情報が無い。**n=194では区別できない。** ただし①なら、
MODEL_V4_RESULT.md の「控除率を超える道は市場の価格ズレを突くしかない」という結論と噛み合う
方向の話ではあるので、追試する価値はある（＝§7の追加データ要求の根拠）。

## 5. 交絡・注意点（次の担当者への申し送り）

1. **開催地とコースが完全交絡**。札幌のレース＝函W/札ダ、中京のレース＝栗坂/CW。
   コース別の複勝率差を「調教コースの良し悪し」と読んではいけない。
   z は (コース,馬場) 内で取っているのでこの交絡は入らないが、**生の `last_1f` を横断比較するのは禁止**。
2. **開始ハロンが揃っていない**。同じ函W内でも 6F/5F/4F から始める馬が混在する。
   `last_3f` は「何ハロン走ってきた末の3F」かで意味が変わるので、本来は `start_f` で層別すべき。
   現在の n では層を切れないので**未対応**。要サンプル増。
3. **欠損は無作為でない可能性**。198頭中4頭に調教行が無い。
   「その期間に追切を実施していない馬」は状態が悪い馬に偏りうる。
   欠損を単に除外すると選択バイアスが入る。**欠損フラグを特徴として持つべき**（未実装）。
4. **馬場は追切日の馬場**であってレース当日の馬場ではない。RULES.md の「馬場は必須」とは別物。
5. `days_to_race` はほぼ定数（4日前が182/194）。**現データでは実質使えない**。
   水曜追い/木曜追いの差を見るには、もっと日付の散らばったサンプルが要る。
6. **`一番時計` フラグ**は n=2 しかないが、netkeibaが明示的に付けている強いシグナル候補。
   将来のサンプルで数が増えたら単独で見る価値がある。

## 7. 拡張側へのお願い（追加データの提案）

### 7.1 何レース分あれば結論が出るか

| 目的 | 必要レース数 | 現実性 |
|---|---:|---|
| **最低ライン**: 「効果があるとしてこの程度以上」の上限を切る | **150〜200R**（約2,500頭） | 8月開催まるごと＋α |
| **推奨**: r=0.10 / OR1.15 級の効果を検出（多重比較込み） | **400〜500R** | 1シーズン分 |
| **本命**: r=0.05 / OR1.10 級（依頼文の効果量）を検出 | **1,500〜2,200R** | 通年×複数年。`hist/` の6,701Rと同スケール |

**まずは 200R（約2,600頭）を目標に**。ここで `rule_audit.py --null-sweep` 相当の
帰無検定（§4.1の方式）が抜けなければ、400R以上に投資する判断ができる。
抜けなければそこで撤退できる — どちらに転んでも200Rは無駄にならない。

### 7.2 収集の設計（ここが数より効く）

1. **全頭・全レース**。発火レースだけ集めると `MODEL_V4_RESULT.md` の警告どおり選択バイアスが入る。
   `PREMIUM_FETCH_LIST.md` はSS/S/A優先だが、**調教の検証用には無選別の連続開催**が要る。
   「ある1日の全12R × 全頭」を単位にするのが最も安全。
2. **調教が無い馬も「無し」と記録する**。§5-3の欠損バイアス対策。行を落とさず
   `馬番,,,,,,,` のような空行か `馬番,NONE` を入れてほしい。
3. **最終追切だけでなく1週前追切も**。「1週前に強め→最終は馬也」という
   仕上げのパターンは、最終追切単体より情報がありそうだが、現データでは1頭1本しか無く扱えない。
4. **日付を散らす**。現データは94%が「4日前」。水曜追い/木曜追い/1週前の差を見るには
   日付の分散が要る（＝ふつうに全開催を集めれば自然に散る）。
5. **坂路の場を増やす**。現在 栗坂65・美坂2 で美浦坂路がほぼ無い。
   坂路レイアウト（§2.3）の検証を美浦でも通しておきたい。
6. **`一番時計` などコース欄の注記をそのまま残す**。加工して落とさないこと。

### 7.3 別ソースで足りないもの

| 欲しいデータ | 用途 | 取得元 |
|---|---|---|
| **出馬表の騎手名**（IDだけでなく短縮名） | 「本番の騎手が追切に跨ったか」の厳密判定（§3.6） | 出馬表ページ。`fetch_race.py` で `jockey_name` を拾うよう1行追加で済む |
| **調教評価（A/B/C）・攻め解説** | netkeibaの人手評価との比較。生タイムの上乗せがあるか | 出馬表の調教欄 |
| **併走相手の馬名・結果** | 「格上に先着」の抽出。番手だけでは強さが判らない | 調教タブ |
| **厩舎の当該週の調教本数** | 陣営の力の入れ方 | 調教タブ |

優先順位は **①全頭・無選別で200R > ②騎手名 > ③1週前追切 > ④調教評価**。
①が無いと他が全部意味を持たない。
